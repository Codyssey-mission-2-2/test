# [팀명] GitHub 협업 프로젝트

Git과 GitHub를 활용하여 이슈 기반 작업, 브랜치 관리, Pull Request(PR), 코드 리뷰, 충돌 해결을 실습하는 팀 프로젝트입니다. 복잡한 기능 구현보다 협업 과정을 경험하고 그 근거를 기록하는 데 목적을 둡니다.

> 초안입니다. `[작성 필요]` 항목을 팀 정보로 바꾸고, 선택한 결과물에 맞게 내용을 수정합니다. 체크박스는 실제 수행 및 증빙 확인 후 표시합니다. 문서 링크는 해당 파일 생성 후 연결됩니다.

### 프로젝트 목표

- GitHub Flow를 적용하여 `main`을 정상 동작하는 상태로 유지합니다.
- Issue를 기준으로 작업을 나누고 PR을 통해 변경 사항을 병합합니다.
- 구체적인 리뷰와 피드백 반영을 통해 협업 경험을 쌓습니다.
- 충돌 및 Git 문제를 해결하고 재현 가능한 기록을 남깁니다.
- 모든 팀원이 결과물 작성과 리뷰에 참여합니다.

## 5. 브랜치 전략 및 협업 흐름

### GitHub Flow 선택 이유

작업 단위 브랜치와 PR 중심의 단순한 흐름이 소규모 팀 협업에 적합합니다.
리뷰와 검증을 거친 변경만 병합하여 `main`을 안정적으로 유지할 수 있습니다.
Issue와 PR을 연결해 작업의 목적과 변경 이력을 추적하기 쉽습니다.

### 브랜치 규칙 초안

| 브랜치 | 용도 | 예시 |
| --- | --- | --- |
| `main` | 항상 정상 동작하는 기준 브랜치 | `main` |
| `feature/<이슈번호>-<작업설명>` | Issue 단위 작업 브랜치 | `feature/12-add-team-profile` |

작업 설명은 영문 소문자와 하이픈을 사용합니다. 팀 합의 후 동일한 규칙을 [협업 가이드](docs/CONTRIBUTING.md)에 문서화합니다.

### 작업 순서

1. 작업 목적과 완료 조건을 포함한 Issue를 생성합니다.
2. 최신 `main`에서 `feature/*` 브랜치를 생성합니다.
3. 작업 및 검증 후 팀 커밋 규칙에 맞춰 커밋합니다.
4. 브랜치를 push하고 `main`을 대상으로 PR을 생성합니다.
5. PR 본문에 변경 사항, 변경 이유, 검증 방법과 `Closes #이슈번호` 또는 `Fixes #이슈번호`를 작성합니다.
6. 다른 팀원의 리뷰를 받고, 질문에 답하거나 수정 사항을 반영합니다.
7. 최소 1명의 승인을 받고 검증을 마친 뒤 PR을 병합합니다.
8. 작업 및 리뷰 증빙을 `SUBMISSION.md`에 기록합니다.

### main 보호 정책

`main`에 Branch Protection Rule을 설정하여 다음 정책을 적용합니다.

- 직접 push를 금지합니다.
- PR을 통한 병합만 허용합니다.
- 병합 전 최소 1명의 승인(Approve)을 요구합니다.

**설정 증빙:** [작성 필요: 설정 화면 또는 확인 기록 링크]

## 6. 커밋 및 PR 규칙

### 커밋 메시지 규칙 초안

형식은 `<type>: <구체적인 변경 내용>`을 사용합니다.

| 유형 | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 기능 추가 | `feat: 문자열 공백 제거 함수 추가` |
| `fix` | 오류 수정 | `fix: 빈 문자열 입력 시 발생하는 예외 수정` |
| `docs` | 문서 작성·수정 | `docs: README에 팀원 소개 링크 추가` |
| `refactor` | 동작을 유지하는 코드 구조 개선 | `refactor: 중복 입력 검증 로직을 함수로 분리` |

`update`, `fix`, `temp`, `wip`, `final`, `bug fix`, `edit file`처럼 변경 대상이나 효과를 알 수 없는 메시지는 사용하지 않습니다.

### PR 본문 예시

```markdown
## 변경 사항 (What)
- 무엇을 추가하거나 수정했는지 작성

## 변경 이유 (Why)
- 작업이 필요한 이유 작성

## 테스트 및 검증 (How)
- 실제 수행한 검증 방법과 결과 작성
- 문서 변경은 내용, 링크, Markdown 표시 상태 등을 확인

## 관련 Issue
Closes #12
```

예시의 `#12`는 실제 작업 Issue 번호로 변경합니다. 모든 `feature/*` 브랜치는 PR을 통해 `main`에 병합합니다.

## 7. 코드 리뷰 및 개인별 기여 기준

### 리뷰 규칙

- 각 PR에는 파일이나 특정 라인을 근거로 한 질문, 대안, 리스크 또는 개선 제안을 최소 1개 남깁니다.
- `LGTM`, `좋아요`만 작성한 리뷰는 실질적인 리뷰로 인정하지 않습니다.
- 각 PR에서 리뷰어와 작성자의 답글 또는 수정 반영 등 상호작용을 최소 1회 남깁니다.
- 작성자는 반영 내용과 관련 커밋을 답글로 안내합니다. 반영하지 않는 의견에는 이유를 설명합니다.
- 각 팀원은 본인 PR 중 최소 1개에서 실제 리뷰 의견을 반영하고 증빙을 남깁니다.

### 모든 팀원이 충족해야 하는 기준

| 항목 | 최소 기준 | 증빙 |
| --- | --- | --- |
| PR 생성 및 병합 | 2개 | 본인이 생성하고 병합 완료된 PR 링크 |
| 다른 팀원 PR 리뷰 | 2개 | 본인 PR을 제외한 리뷰 링크 |
| 리뷰 반영 | 본인 PR에서 1회 이상 | 리뷰 코멘트, 반영 커밋·수정 및 답글 |
| 트러블슈팅 기록 참여 | 1개 시나리오 이상 | 이름과 역할이 명시된 기록 |
| 선택 결과물 기여 | 1건 이상의 커밋 | 결과물 변경 커밋 링크 |

## 8. 충돌 해결 및 Git 트러블슈팅

### 충돌 해결

팀 전체에서 최소 2회의 충돌 해결 기록을 남기며, 이 중 최소 1회는 다음 중 하나에 해당해야 합니다.

- 같은 파일의 같은 hunk(인접 라인)를 서로 다르게 수정한 충돌
- 한쪽의 파일 이동·이름 변경·삭제와 다른 쪽의 내용 수정으로 발생한 충돌 또는 머지·리베이스 문제

충돌 발생 시 작업자와 관련 변경 작성자가 최종 내용을 협의하고, 해결 후 결과물을 검증합니다. 담당자는 발생 원인, 관련 브랜치, 해결 과정, 검증 결과, 참여자와 커밋·PR 링크를 [충돌 해결 기록](docs/conflict-resolution.md)에 작성합니다.

### Git 트러블슈팅

아래 네 가지 시나리오를 팀 전체 기준으로 모두 수행합니다. 각 팀원은 최소 1개 시나리오의 기록 작성에 참여하며 이름과 역할을 남깁니다.

| 시나리오 | 실습 내용 | 기록 상태 |
| --- | --- | --- |
| `git commit --amend` | 최근 커밋 메시지 수정 | 미작성 |
| `git reset --soft HEAD~1` | 로컬 커밋을 취소하고 변경 사항 유지 | 미작성 |
| `git revert` | 원격에 push된 커밋의 변경을 취소하는 새 커밋 생성 | 미작성 |
| `git stash` / `git stash pop` | 미완료 작업 보관 후 브랜치 전환 및 작업 복원 | 미작성 |

실습은 `main` 보호 정책을 지키며 작업 브랜치에서 진행합니다. `amend`와 `reset --soft`는 아직 push하지 않은 로컬 커밋으로 실습하고, `revert`는 작업 브랜치에 push한 커밋을 대상으로 수행합니다.

실행 전후 상태, 명령어, 결과 및 참여자별 역할은 [트러블슈팅 기록](docs/troubleshooting-log.md)에 작성합니다.

## 10. 제출 전 확인

- [ ] 3~5인 팀 및 저장소 구성을 완료했다.
- [ ] 기본 파일·폴더를 구성하고 `main` 보호 규칙을 설정했다.
- [ ] 협업 가이드를 팀원이 분담하여 작성하고 GitHub Flow 선택 이유를 기록했다.
- [ ] 모든 작업을 Issue로 만들고 PR 본문에 연결했다.
- [ ] 커밋 메시지가 변경 대상이나 효과를 구체적으로 설명한다.
- [ ] 모든 팀원이 PR 2개 이상을 생성하고 병합했다.
- [ ] 모든 팀원이 다른 팀원 PR에 리뷰를 2개 이상 작성했다.
- [ ] 모든 PR에 실질적인 리뷰 코멘트와 작성자·리뷰어 상호작용이 있다.
- [ ] 모든 팀원이 본인 PR에서 리뷰 의견을 1회 이상 반영했다.
- [ ] 충돌 해결을 2회 이상 기록했으며 비자명 충돌을 1회 이상 포함했다.
- [ ] 네 가지 Git 트러블슈팅을 수행하고 모든 팀원의 기록 참여를 확인했다.
- [ ] 선택 결과물의 완성 기준과 팀원별 기여 커밋 1건 이상을 충족했다.
- [ ] 결과물 링크·목차 또는 사용 예시를 README에 작성했다.
- [ ] `SUBMISSION.md`에 팀원별 증빙 링크를 정리했다.
- [ ] 초안의 미작성 항목을 채우고 문서 링크가 정상적으로 연결되는지 확인했다.
