# CONTRIBUTING

이 문서는 팀의 Git 브랜치 전략(GitHub Flow)과 브랜치 네이밍 규칙을 정의한다.

## 1. 왜 GitHub Flow인가

> - 브랜치가 `main`과 `feature/*` 두 종류뿐이라 구조가 단순해 팀원 누구나 빠르게 익힐 수 있다.
> - 작은 단위로 자주 병합·배포하여 빠른 피드백과 지속적인 배포(CD)를 지향한다.
> - 작업마다 독립 브랜치를 사용해 동시 작업 시 충돌을 줄이고, PR 리뷰로 품질을 확보한다.

## 2. 브랜치 전략

| 브랜치 | 역할 | 규칙 |
|---|---|---|
| `main` | 항상 배포 가능한 상태 유지 (깨지지 않는 상태) | 직접 push 금지, PR을 통해서만 병합 |
| `feature/*` | 기능 개발·버그 수정 등 작업 단위 브랜치 | `main`에서 분기, 병합 후 삭제 |

- `develop`, `release/*`, `hotfix/*` 브랜치는 사용하지 않는다.
- 긴급 수정도 사소한 변경으로 보고 `feature/*` 브랜치로 작업하여 PR로 병합한다.

### main 브랜치 보호 규칙 (권장)

- Direct push 금지
- PR 승인(Approve) 최소 1명 이상 필수
- CI(빌드/테스트) 통과 후에만 병합 가능
- 병합 전 최신 `main` 반영 (브랜치 up-to-date)

## 3. 브랜치 네이밍 규칙

### 형식

```
feature/<이슈번호>-<작업-내용-요약>
```

### 규칙

1. 접두사는 항상 `feature/`를 사용한다.
2. 이슈번호가 있으면 앞에 붙인다. (예: `feature/12-user-login`)
3. 작업 내용은 **영문 소문자 + 숫자 + 하이픈(`-`)** 만 사용한다. (kebab-case)
4. 공백, 대문자, 언더스코어(`_`), 한글, 특수문자는 사용하지 않는다.
5. 한 브랜치에는 한 가지 작업만 담는다.
6. 길이는 짧고 명확하게 작성한다. (3~5단어 권장)

### 예시

| 구분 | 예시 |
|---|---|
| 기능 개발 | `feature/12-user-login` |
| 버그 수정 | `feature/27-fix-login-error` |
| 문서 작업 | `feature/31-update-readme` |
| 리팩토링 | `feature/45-refactor-auth-service` |
| 이슈번호 없음 | `feature/add-search-filter` |

### 잘못된 예시

| 예시 | 이유 |
|---|---|
| `Feature/UserLogin` | 대문자 사용 |
| `feature/user_login` | 언더스코어 사용 |
| `feature/로그인기능` | 한글 사용 |
| `login` | 접두사 누락 |
| `feature/fix-everything` | 작업 범위가 불명확 |

## 4. 커밋 메시지 규칙

### 형식

```
<type>(<scope>): <subject>

<body>

<footer>
```

- `<type>`과 `<subject>`는 필수, `<scope>`, `<body>`, `<footer>`는 선택이다.
- 각 영역 사이는 빈 줄로 구분한다.

### type 목록

| type | 설명 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 (README, CONTRIBUTING 등) |
| `style` | 코드 동작에 영향 없는 포맷팅 변경 (공백, 세미콜론 등) |
| `refactor` | 기능 변화 없는 코드 구조 개선 |
| `test` | 테스트 코드 추가·수정 |
| `perf` | 성능 개선 |
| `build` | 빌드 설정, 의존성 변경 |
| `ci` | CI/CD 설정 변경 |
| `chore` | 기타 잡무 (위 분류에 속하지 않는 변경) |
| `revert` | 이전 커밋 되돌리기 |

### 작성 규칙

1. **subject**는 50자 이내로 작성하고, 끝에 마침표를 붙이지 않는다.
2. subject는 **무엇을 했는지** 간결하게 쓴다. (예: `로그인 API 구현`)
3. **body**는 변경 이유와 내용을 설명하며, 한 줄은 72자 이내로 줄바꿈한다. (필요한 경우에만 작성)
4. **footer**에는 관련 이슈를 연결한다. (예: `Closes #12`, `Refs #30`)
5. 하나의 커밋에는 **하나의 목적**만 담는다. (기능 추가와 포맷팅을 섞지 않는다.)
6. type은 영문 소문자, subject와 body는 한글로 작성한다. (고유명사, 기술 용어는 영문 허용)
7. 빌드가 깨지거나 테스트가 실패하는 상태로 커밋하지 않는다.

### 예시

```
feat(auth): 로그인 API 구현
```

```
fix(order): 주문 취소 시 재고가 복구되지 않는 문제 수정

취소 처리 로직에서 재고 반영 호출이 누락되어 있었다.
취소 트랜잭션 안에서 재고 복구를 수행하도록 변경했다.

Closes #27
```

### 잘못된 예시

| 예시 | 이유 |
|---|---|
| `수정` | 무엇을 바꿨는지 알 수 없음 |
| `fix: 버그 수정.` | 구체적이지 않고 마침표 사용 |
| `Feat: 로그인 구현` | type에 대문자 사용 |
| `feat: 로그인 구현하고 README 수정하고 디자인 변경` | 여러 목적이 한 커밋에 섞임 |
| `update`, `wip`, `asdf` | 의미 없는 메시지 |

## 5. 작업 흐름 (GitHub Flow)

```
main ──●────────────────────●────▶  (항상 배포 가능)
        \                  /
         ●──●──●  feature/12-user-login
         (commit) (PR → 리뷰 → 병합)
```

### ① 브랜치 생성

최신 `main`에서 작업 브랜치를 생성한다.

```bash
git checkout main
git pull origin main
git checkout -b feature/12-user-login
```

### ② 커밋 작성

작업 단위별로 커밋하며, 메시지는 [4. 커밋 메시지 규칙](#4-커밋-메시지-규칙)을 따른다.

```bash
git add .
git commit -m "feat(auth): 로그인 API 구현"
```

### ③ Pull Request 생성

원격에 push한 뒤 `main`을 대상으로 PR을 생성한다.

```bash
git push origin feature/12-user-login
```

- PR 제목에 작업 내용을 명확히 작성한다.
- 관련 이슈를 연결한다. (예: `Closes #12`)
- 변경 사항, 테스트 방법을 본문에 기록한다.

### ④ 리뷰 및 피드백

- 팀원이 코드를 검토하고 피드백을 남긴다.
- 피드백 반영 후 같은 브랜치에 추가 커밋한다.
- 코드 품질 향상과 버그 조기 발견이 목적이다.

### ⑤ 병합

- 승인과 CI 통과 후 `main`으로 병합한다.
- 병합 완료 후 `feature/*` 브랜치는 삭제한다.

### ⑥ 배포

- `main`에 병합된 변경 사항은 자동 또는 수동으로 배포 프로세스를 시작한다.
- 배포 단계에서 테스트, 빌드, 배포가 수행된다.

## 6. 주의사항

- `main`에 직접 커밋하거나 push하지 않는다.
- 브랜치는 오래 유지하지 않고 작은 단위로 자주 병합한다.
- 테스트·검증 없이 병합하지 않는다. (배포 위험 방지)
- 프로젝트 규모가 커지거나 복잡한 배포 요구사항(다중 버전 관리 등)이 생기면 브랜치 전략을 재검토한다.
